# Audit 2026-08-26: the read/write identity split

> Session handoff. Verdict on "public always-served reads + identified writes on an isolated
> pre-federation node". 13-agent workflow, 53 claims, 159 adversarial verdicts, 22 refuted or
> weakened. Every `file:line` below was spot-checked against source at `02bb4dbb` (v0.3.0).

---

## Verdict

**Keep the split. Right seam, survives federation.** Two problems with the read half as stated:

1. It is not unconditionally true (VIS-13 defaults every resource to `T0` private).
2. Shipping the stream as-is publishes live commit and cancel tokens.

**Use this sentence instead of "availability can always be served":**

> Writes always require an authenticated principal. Reads require a grant unless the owner has
> explicitly opted that resource out of the T0 default. Where published, the anonymous read is keyed
> for **metering, not authorization**, cost-bounded, coarsened to D0, and best-effort under write
> load. Composition stays topology-free (FED-09), so the read is portable data forever. **No read
> surface, pull or push, ever carries an entity identifier or free text.**

That last clause is currently violated everywhere.

## The crux: identity without federation? Yes.

| | What | Trust direction | Gate |
|---|---|---|---|
| **Federated identity** | many issuers, one node; validate a token you did not mint, key on `(iss, sub)` | inbound only | none |
| **Federated nodes** | many operators, cross-org audience, `.well-known`, peer verify | bidirectional | FED-08 |

Only the second is what FED-02 / invariant-confluence constrains. **This proposal is already the
docs' own P4a** (`AUTH-ARCHITECTURE.md` §10 sequences it exactly).

Wording bug to fix: `REQUIREMENTS.md:267` and `:392` say "identity"/"signing" unqualified, which
reads as forbidding this. They mean *node* identity. One line each.

## Performance: the cliff is at ONE writer

Reads and writes contend on the same per-resource `RwLock` and **the writer holds it across the WAL
fsync**. Documented in our own comment at `queries.rs:232-235`; mechanism at `engine/mod.rs:470-481`
(`persist_and_apply` awaits `wal_append` while holding `&mut ResourceState`).

| writers on resource | read p50 | reads/sec |
|---|---|---|
| 0 | 51 us | ~15,000 |
| **1** | **2,997 us** | **328** |
| 8 | 19,875 us | 56 |

At 1 writer, reads/sec == writes/sec: the read path is fully serialized behind fsync, one read per
commit. Propagates up the tree (`collect_inherited_rules` read-locks every ancestor).

**Caveats:** agent-built harness on this Mac, not our benches. macOS `sync_all` is `F_FULLFSYNC`, so
write figures are a pessimistic ceiling; `wal.rs:183` is `sync_all` where HW-07 requires
`fdatasync`. Linux + PLP NVMe unmeasured, could be 10-20x better and would move every ratio here.
Two runs disagreed on read baseline (51 vs 95 us) but agreed on the ratios.

**Our benchmark cannot see this.** `benches/stress.rs:298` queries a 365-day window against
`MAX_QUERY_WINDOW_MS = 90 days` (`limits.rs:8`) and `.unwrap()`s, so phase 3 panics and phase 4 has
never run. It also mints a fresh ULID dbname per client, so it cannot measure same-resource
read-under-write contention at all.

**Real fix (not a workaround):** move the fsync out of the write guard. Apply in memory under the
lock, release, then await durability before acking. Failure direction is safe: a reader may see an
allocation a crash later loses, which shows *less* availability, never a double-book.

**Identity on writes is performance-positive.** Ed25519 verify is 28-70 us against a 2.6 ms commit
(2.7%). It buys the only key a per-identity hold cap can use, and that cap bounds the 46x collapse
above. PROTO-AUTH-08 is also an uncounted perf fix: today an unauthenticated startup packet can
mint `MAX_TENANTS = 1000` WAL files, each with reaper + compactor + GC tasks.

Subsequent cliffs: NOTIFY fan-out loss (66.5% delivery at 1 subscriber, 47.8% at 10, 27.5% at 100
under one legal 1,000-row batch, so NOTIFY is a purge tick, never a payload feed); 256-connection
ceiling if pgwire is ever the public stream; read CPU saturation at 64 connections; WAL compaction
inline in the writer task (10.6 ms at 1k intervals, ~660 ms extrapolated at 1M, firing every ~3 s at
default `DELTAT_COMPACT_THRESHOLD = 1000`).

## One-way doors (get right now)

1. **Never publish an entity Ulid or free text on any read or push surface.** Leaked capabilities
   cannot be recalled. Extend AUTHZ-07's fix list beyond `label` + hold Ulid to booking and rule ids.
2. **Principal key = local opaque `principal_id` PK, `(iss, sub)` UNIQUE secondary. Never email.**
   (Cross-issuer email collision at unequal assurance is an account-takeover primitive. IDENT-03
   forbids it but never says why.) Note IDENT-03 contradicts SHR-01, whose grantee is already
   `principal_id`; resolve toward SHR-01.
3. **Never let the caller name the tenant, in any spelling.** Live bug at `wire.rs:98-101`.
   **Settle audience granularity before the first token is minted:** PROTO-AUTH-04 says one audience
   per node, MCP-A1 says one per tenant with the stronger argument. Unresolved contradiction.
4. **Ed25519, distinct `kid` for `use:cap` vs node identity, from day one.** Never HMAC.
5. **WAL format, most dangerous item.** Adding a field to an existing `Event` is NOT additive: it is
   upgrade-breaking and data-destroying (mid-log the node will not start; at tail `Wal::open`
   truncates + fsyncs and destroys the booking). Root cause: `read_header` (`wal.rs:41-64`) parses
   the version and discards it, so `scan` cannot branch. **Build the migration hook first**, then
   batch into one v2: `HoldCommitted`, `booking_group`, `label -> external_ref`, **ms -> microsecond
   widening (urgent: `model.rs:11` is ms, FORMAT.md mandates us, bytes identical, CRC passes,
   version check passes, every stored instant silently divides by 1000)**. Adding a new *variant* is
   the safe class.
6. **Holds require identity from the start.** Loosening later is additive; tightening is not, and
   holds already in the WAL carry no principal so they can never be attributed retroactively.

**Reversible, defer:** IdP vendor, capability library, tenant path vs subdomain, L1 cache design,
R0.5 accountable-but-not-enrolled hold ring. Gap that kills the obvious R0.5: **Web Bot Auth
identifies an agent fleet, not a requester**, so a hold cap keyed on it starves a whole vendor's
users or does nothing.

## Do not re-litigate (refuted this session)

1. "Write-side controls can be added later." **No.** PROTO-AUTH-08 is a live confidentiality breach
   AND the prerequisite for the read ACL's principal.
2. "`DELTAT_TENANT_PASSWORDS` mitigates the tenant problem." **No, it fails open.**
3. "PROTO-AUTH-08 is strictly more restrictive so no regression." **No**, see Phase 1 above.
4. "A stale or hallucinated read cannot become a booking." **Not a kernel property.**
   `INSERT INTO bookings` -> `confirm_booking` takes the caller's span with no hold
   (`sql.rs:110-115`); batch form does 1,000 at once. Safety lives in the *absence* of an MCP tool.
5. "Payment-as-authorization is the strongest lever." **Retracted.** Stolen-card economics price the
   attack at zero for the attacker; a synchronous PSP authorize is 100-500 ms against a 2.75 ms
   hold; it creates a second principal namespace with no durable cancel path. Keep P2, land the
   principal table first so `psp_customer_id` is a row on a `principal_id`, not a key.
6. "Fixing AUTHZ-07 breaks passing tests." **No test asserts payload content.**
7. "One batch insert guarantees a Lagged for every subscriber." **False**, loss scales with fan-out.

## Booking: the forgotten half

- **Modify does not exist.** `parse_update` (`sql.rs:344-417`) handles resources, rules, holds only.
  Reschedule = DELETE + INSERT, two fsyncs, ~5 ms window for a competitor. A rule can move
  atomically; a booking cannot.
- **`HoldCommitted` does not exist.** FED-AUTH-11 and PAY-01 both fire capture on it. `commit_hold`
  emits `HoldReleased` + `BookingConfirmed` with no link, and `confirm_booking` emits the same
  `BookingConfirmed`, so an edge cannot distinguish hold-backed commit from operator direct-book.
- **No by-id read** for bookings/holds, so "where is my reservation" pulls every other guest's label
  into the trusted process and filters. The index already exists (`store.rs:16, 86-88`), ~30 lines,
  no format change.
- **`delete_resource` mass-cancels invisibly** (`mutations.rs:100-136`): unmaps every interval, one
  `ResourceDeleted`, no `BookingCancelled`, then drops the broadcast channel.
- **No idempotency.** `error.rs:91` maps `Conflict` AND `CapacityExceeded` to SQLSTATE 40001 with
  `is_retryable() == true`, so MCP-T4 tells agents to retry a genuinely occupied slot forever.
  `RETRY` has no producer. Worse: a retry inside the 5 s reaper window inserts a **second interval
  with the same id** (`insert_interval` does not dedupe, `conflict.rs:124` skips expired holds);
  release removes one copy and unmaps `entity_to_resource`, leaving the survivor unreachable
  forever, blocking the span, surviving WAL replay.

**The decision that unblocks the rest: what is the guest's durable handle?** Today it defaults to
the booking Ulid as a bearer capability, which is exactly what makes a public stream permanently
unsafe. Mint a signed receipt at commit over
`{booking_id, resource_id, span, principal_ref, aud, kid}`. Gives MCP-O2 a home, makes an
anonymous-but-paid guest cancellable weeks later, removes the reason the Ulid must stay secret.
Cost: a second synchronous durable write in series with a 2.6 ms path. Share the group commit.
